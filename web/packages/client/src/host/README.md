# Core host

`CoreHost` runs one account's core (replica, realtime client, outbox, queries) behind the `CoreEndpoint` interface from `@inline/core-protocol`. It knows nothing about workers or tabs; `link` carries the interface there.

## API

```ts
const host = new CoreHost({
  buildId,                                  // in `hello` and the `core` resource
  openStorage: (userId) => HostStorage,     // e.g. openOpfsHostStorage(userId)
  createTransport?: (userId) => Transport,  // default: WebSocket
  realtime?: { url, buildNumber, layer, sync, connection, logLevel },
  pageSize?: 50,                            // messages per window page
  logOutTimeoutMs?: 3000,                   // how long sign-out waits for LOG_OUT
  media?: { store, accountKey, fetch, rpc, imagePreparer, clock, settings } | false,
                                            // the account's MediaCore; defaults: OPFS byte store
                                            // (memory without OPFS), globalThis.fetch, RPCs over the socket
  searchStartDelayMs?: 1000,                // local search backfill starts this long after the first ready publish
  eraseStorage?: (userId) => Promise<void>, // erase a replica without opening it (browser: eraseOpfsHostStorage)
})

host.post(command) / host.subscribe(listener)   // the primary context
const context = host.openContext()              // another UI context (own subs, revisions, rows)
await host.close()                              // = shutdown(): stop without erasing; resolves after storage closes
await host.idle()                               // bounded work done (tests, handoff)
host.coreResource()
await host.finishPendingErase(userId)           // finish an erase a killed core left (boot sweep); true if there was one
```

In the browser pass `media: { imagePreparer: browserImagePreparer }` (from `../media`) so photos are measured, compressed and previewed in the worker; without one, photos keep the UI's width and height hints and only JPEG and PNG go as photos.

`HostStorage` is `{ store, kind: "persistent" | "memory", erase() }`. `openOpfsHostStorage(userId, location?)` opens the OPFS replica, falls back to memory only when the browser cannot keep one, and erases with `eraseOpfsSqliteReplica`. Tests use an in-memory SQLite "disk" (`__tests__/fixtures.ts`).

Files: `core-host.ts` (commands, phases, contexts, publishing, sign-out), `account-core.ts` (one session: `Db`, `RealtimeClient`, in-memory `AuthStore`, committed view, watchers, per-message chains), `intents.ts`, `overlay.ts` (display overlays of edits and deletes), `new-messages.ts` (the `newMessages` feed), `sync-health.ts` (`HostSyncEngine`: stalls and live delivery), `windows.ts` (chat windows and `ensure`), `drafts.ts`, `message-identity.ts`, `peers.ts`, `tracked-store.ts` (storage-full detection), `storage.ts`. Added on 17 November (host data): `durable.ts` (host records: durable intents the outbox registry cannot restore), `settings-intents.ts`, `media.ts` (`HostMedia`: media subscriptions, nearby hints, URL refresh), `attachments.ts` (`AttachmentCoordinator`: staging and media sends), `compose.ts` (compose activity), `search.ts` (`HostSearch`). Added by contract-2: `participants.ts` (participant intents), `chat-media.ts` (`HostChatMedia`: `chatMedia` server pages), `remote-search.ts` (`HostRemoteSearch`: server message and people search), `erase.ts` (the sign-out erase marker and `finishPendingErase`); in `../queries/`, `chat-media.ts` (which stored messages a filter lists); new transactions `add-chat-participant.ts`, `remove-chat-participant.ts`, `search-messages.ts`, `search-users.ts`. The materializer is in `../queries/` (`membership.ts` for member, group, folder and settings rows and orders). The new transactions it uses are `../realtime/transactions/log-out-rpc.ts`, `submit-message-form.ts`, `update-dialog-notification-settings.ts`, `update-dialog-archived.ts`, `read-dialog.ts`, `dialog-field.ts`, `send-compose-action.ts`, `send-media-message.ts`.

## Guarantees

- **Phases.** `signedOut` until `session start`; then `starting`, `ready`, or `outdated` (replica from a newer schema, left untouched) or `failed` (with a user-safe `failure`). Subscriptions made while starting get their first result when ready, never an empty flash.
- **Committed state only.** Queries read a `CommittedView` fed solely by `Db.subscribeToResidentChanges` batches, which `Db` delivers after their storage transaction commits. Live memory can be ahead; the view never is. The one exception is the display of intents that are not replay-safe: `OverlayView` applies open edits and deletes on top of the committed view (and pending reactions ride on committed rows as `reactionIntents`, which are never written to disk). Their base is always committed; the overlay is memory only and dies with the core.
- **Patches.** After commits, each context gets one patch (commits in the same task are coalesced) containing only changed rows, list splices and resources, with a contiguous revision. A context's first message is a snapshot; `resync` answers with a snapshot one revision on, including `settled`. Rows no subscription of a context needs are removed in the same patch.
- **Dependencies.** Each subscription records what it read (object refs, whole kinds, message chats); a change outside them does not recompute it. The sidebar depends on every dialog and chat, on each listed chat's last message and draft, and on the spaces it shows.
- **Sidebar rows** carry what a row view shows (Mac `ChatListItemSnapshot`): per dialog, the chat (with `lastMessageRowId`), the peer user, the last message row and its sender, the draft row, the space row and a reply thread's parent chat; `DialogRow` has `followMode`, `notificationMode`, `unreadMentionsCount`, `unreadReactionsCount`, `folderId`. Each chat's last message is read from disk before the core is `ready`, so the first sidebar result has its previews; a last message that later turns out missing is read once on demand (`wantMessages`). Diffing holds: a new last message in one chat sends that chat's message, chat and dialog rows, a `remove` for the previous last message, and a list change only when the order moved. Message rows are memoized per stored object, so recomputing the sidebar maps only what changed.
- **Sidebar order** follows the Mac app: hidden dialogs never show; `inbox` = not archived and open or pinned, `all` = not archived, `archived`; pinned first by `pinnedOrder`, then `inbox` by `order` and the others by last activity; ties by dialog ID descending.
- **Chat windows.** One window per chat (the replica's `FullChatWindowState`), shared by subscriptions. Opening reads the local window first, then refreshes from the server; a spinner (`loading: "initial"`) shows only for an empty window. `ensure older/newer` pages from the server while connected and from the replica offline; an empty or short server page sets `hasOlder: false`.
- **Intents.** `accepted` after the intent and its optimistic rows commit; `confirmed` after the server result commits; `rejected` with a reason (`invalid`, `server`, `storageFull`, `notSignedIn`, `unavailable`, `unsupported`, `offline`), or `uncertain` (ambiguous, abandoned settlement, or the core stopped). A repeated `tx` gets its latest result. Intents posted after `session start` wait for it.
- **Replay-safe intents** (`sendText`, `markRead`, `setDialogOpen`) go through the durable outbox and wait in it offline.
- **Intents that are not replay-safe** (`editText`, `deleteMessages`, `react`, `invokeAction`, `submitForm`; the server has no idempotency key for them) never enter the outbox and are not restored after a restart. Offline they are `rejected` with `offline` before anything shows. They are sent once; one in flight when the connection drops settles `uncertain` and is not resent (the realtime client's ambiguous-result rule).
  - `react`: the reaction transactions' optimistic `reactionIntents` overlay (committed with the row, never written to disk); `accepted` after that commit.
  - `editText` (invariant 4): the replica keeps the confirmed base; open edits live in `PendingOverlay`, in order, and queries read messages through `OverlayView`, so the shown text is the newest open edit, else the base. Edits of one message are sent one at a time in order (`AccountCore.serialize`). A confirmed edit's server update commits before its result resolves, so removing the overlay never shows an older text; a failed or uncertain one falls back to the newest remaining edit or the base. Nothing is undone; the display is recomputed. Not guaranteed: the overlay is memory only, so an edit open when the core stops is lost (reported `uncertain`), and an `uncertain` edit shows the base until sync delivers the server's version; edits made on another device while one is open here are hidden behind it until it settles.
  - `deleteMessages`: hides the rows (overlay) until it settles; a confirmed delete's update removes them first, a refused or uncertain one shows them again. `clientKeys` name sends from this device: one still in the outbox (queued or failed) is cancelled locally in one commit and the server never sees it; one already on the wire is waited for (`CANCEL_LANDING_TIMEOUT_MS`), its server row kept hidden, then deleted on the server (the Mac `CancelledSends`).
  - `accepted` for edit and delete means admitted and shown in this session, not durable: nothing on the device changes until the server answers.
  - `invokeAction` and `submitForm` (`INVOKE_MESSAGE_ACTION`, the form as `action_id = form_id` with `MessageFormSubmission`): `confirmed` carries the bot's `answer` (toast or alert) when it answered within `ACTION_ANSWER_TIMEOUT_MS`.
- **Results across a restart.** A `sendText` re-posted to a later core (same `tx` or same client key) whose send is still in the outbox is answered `accepted`, then followed in the replica to its outcome: `confirmed` when the server assigned its ID, `rejected` (`server`) when it failed, `uncertain` if it vanished. After it landed, a re-post sends again with the same random ID and the server deduplicates (`confirmed`, one message).
- **New messages** (`newMessages` query, `new-messages.ts`): a message joins the feed when a push or catch-up page delivered its `newMessage` (seen by `HostSyncEngine` before it applies), its committed batch inserts it for the first time, and it is incoming, not silent, above the dialog's read frontier and at most `NEW_MESSAGES_RULE.maxAgeSeconds` old; history pages, repairs and disk reads never qualify. At most `limit` entries, each released `retainSeconds` after it arrived (a timer). Each subscription lists only what arrived after it started. Without the host's sync engine (`realtime.sync` injected or `false`) the feed stays empty.
- **Sync health.** `HostSyncEngine` reports stalls (`onBucketStalled`) and the points where they clear (a new connection, a retry); the `core` resource carries `stalledSync` while any bucket is stalled; the `retrySync` intent calls `retryStalledBuckets()` and is `confirmed` at once.
- **Row identity.** A send keeps `${chatId}:r${clientKey}` after the server assigns its ID (`MessageIdentity`).
- **Drafts** are local-only: saved with `Db.commit` under the existing `MessageDraft` model (DMs by peer user, other chats by chat), `accepted` then `confirmed` after the commit; an empty draft deletes; a lower revision is a no-op.
- **Sign-out and revocation** (invariant 10, `erase.ts`). In order: the account becomes unusable at once (`core.signingOut: true`; every intent, drafts included, is `rejected` with `notSignedIn` from here on); an erase marker is written to the account's byte store (`accounts/<accountKey>/erase-pending`, outside the SQLite pool); on a sign-out from a UI while connected, `LOG_OUT` is handed to the socket (`AccountCore.sendLogOut`, best-effort, its answer never awaited); realtime stops and the replica closes (nothing is written after this), media is erased, the replica (with its search index) is erased, the media files are removed, and the marker goes. Only then does `phase` become `signedOut`, with `erased: "complete"`, or `erased: "failed"` when any step failed (the marker then stays). Every subscription empties (`connection: "sessionRevoked"` after a revocation). A worker killed at any point after the marker is written leaves the marker: the next `session start` of that account (or `host.finishPendingErase(userId)`, for a boot sweep) erases the replica (`eraseStorage`, or open-close-erase) and the media files before anything opens them, and a start whose leftover erase fails ends `failed` without opening the replica. A revocation never sends `LOG_OUT`; a token the server clears in answer to it is not taken for a revocation. A repeated `session start` for the running user is a no-op.
- **Signals** go to `ConnectionManager.setNetworkAvailable`, `setAppActive` and `systemDidWake`; offline shows `connection: "waitingForNetwork"`.
- **Storage full.** A quota failure on an intent's commit rejects it with `storageFull` and sets `storage: "full"`; the next successful write clears it.

- **Member lists.** `chatParticipants` and `spaceMembers` read the replica's grants and members (committed view) in the Mac's order; on first subscribe in a session the host fetches `GET_CHAT_PARTICIPANTS` / `GET_SPACE_MEMBERS` unless the chat or space is marked complete (`participantRosterComplete`, `memberRosterComplete`), and the `roster` resource says `loading`, then `complete` (or `failed`; the next subscribe fetches again). After that the list follows the replica: one member joining sends that member's row and their user, and a list splice.
- **Settings intents.** `setDialogFollow`, `setDialogPinned` and `markUnread` go through the realtime outbox (its registry restores them). `updateUserSettings`, `setDialogNotifications`, `setDialogArchived` and `readAll` are new transactions the registry (owned elsewhere) does not know, so the host keeps them durable itself (`durable.ts`): a `pending_transaction` row of type `host_intent`, written with status `failed` so the realtime client never restores or runs it, committed with the transaction's prepared state and optimistic rows (`accepted` after that commit); the result's commit deletes it; after a restart the host re-applies and resends it. All are replay-safe on the server and retried after a lost acknowledgement or a dropped connection. `userSettings` fetches `GET_USER_SETTINGS` once per session when the replica has none.
- **Media.** One `MediaCore` per account, opened after the replica (byte store, RPC over the realtime socket with an abort signal, injected `fetch`), online only while connected, closed on shutdown and erased on sign-out and revocation (invariant 10 covers media: jobs, staged sources, cache). A `media` subscription resolves its reference against the committed message (reading it from disk when not resident), pins the cached file while held, and claims it on the scheduler (`visible` within auto-download limits, or `opened`); its resource goes `absent`, `queued`, `downloading` (with bytes), `ready` (with a `Blob` handle) or `failed`. `mediaHints` sets a context's nearby set (the scheduler gets the union). An expired signed URL (a 403) is refreshed through `GET_MESSAGES`: the fresh message commits into the replica, so rows carry the new URL, and the download continues with it.
- **Attachments and media sends** (`attachments.ts`). `attachFile` stages the bytes and the job in the media core and the info beside them (`attachments/<id>.json` under the account's media root), then starts the upload. `sendMedia` commits a host record (kind `mediaSend`, naming the attachment, random ID and temporary message ID) with the optimistic message row in one transaction; the row carries `upload` and a `media` describing the local file. Then: wait for the upload's completion (persisted by the media core before anyone is told), `SEND_MESSAGE` with the server's media ID under the record's random ID; the result and the record's deletion commit together, then the bytes are cached under the server's file and the job is released. A restart at any step resumes from the record; a send that may have reached the server goes again under the same random ID, which the server deduplicates. Sends of one chat go out in acceptance order. A failed upload or a refused send leaves the row `failed` and the record kept; `retrySend` retries the upload (a fresh server upload if the old one failed) and sends. `deleteMessages` by client key cancels: the upload is cancelled, the row and record removed in one commit; a send already on the wire is waited for and deleted on the server. Attachments no send names are released at start when complete or older than an hour.
- **Compose activity** (`compose.ts`, ephemeral, never in the replica): outgoing `typing` at most once per 3 s; other actions sent at once and refreshed every 3 s until `null` or another action; a stop only after something was sent. Incoming `updateComposeAction` pushes (seen by `HostSyncEngine` before they apply) are kept per chat and user, expire 6 s after their last refresh, end on `NONE` or a new message from that user (except agent work), and are cleared when the connection drops.
- **Local search** (`search.ts`). The engine is created after the replica opens (on the SQLite replica only; `TrackedStore` passes the search store through), starts its backfill `searchStartDelayMs` after the first publish while ready, and is stopped before the store closes (shutdown, sign-out, revocation). Its state is `CoreResource.searchIndex`. `searchMessages` hits get `chatTitle` (the peer's display name for a direct chat, else the title), `peerUserId` and `spaceId` from the committed view. Each request is aborted when its subscription is replaced or released; a late result is dropped.

- **Participants** (`participants.ts`). `addChatParticipants` (one `ADD_CHAT_PARTICIPANT` per person or group) and `removeChatParticipant` are host records (`addParticipant`, `removeParticipant`), all of one intent committed with their optimistic grant rows in one transaction (`accepted` after it), sent when connected, retried after a lost acknowledgement, resent by the next core. The add's optimistic row appears only for people (and groups) already on the device; the server's answer adds the rest. A refusal marks the roster incomplete and fetches it again (`AccountCore.refreshRoster`) instead of guessing a rollback. A `tx` re-posted to a later core while its records exist follows them (`confirmed` when the grants reached the asked state, else `rejected`), so it is never applied twice.
- **Chat media** (`chat-media.ts`, `queries/chat-media.ts`). Local first: on subscribe the chat's stored matches are read from disk (`Db.scanChatMessages`: newest first, a backwards walk of the `message` primary key, at most 50 matches or 2,000 rows read, ~5 to 7 ms on a chat of 100,000 messages) and the subscription's first result waits for that read, so media on the device lists in the first frame. The list is the resident matches plus every key a disk read or a server page of this subscription named (read from disk once when not resident), newest first. `SEARCH_MESSAGES` pages (50, filter, `offset_id`) start on subscribe while connected or when the connection returns; `ensure older` reads on from disk (up to 5,000 rows) and fetches the next server page. Pages commit through `upsertMessage` like `GET_MESSAGES` (rows only, no coverage). `loading` is the server page only; `hasMore` is the server's (false after a short page) once it answered, before that whether disk has more.
- **Server search** (`remote-search.ts`). `searchServerMessages` (`SEARCH_MESSAGES` with the query as one ANDed query, newest first; ranges from `search/`'s matcher) and `searchUsers` (`SEARCH_USERS`, the account left out) are request and answer like local search; nothing is written; offline or malformed fails at once.
- **Sends** carry `draftRevision` (the draft is deleted in the send's own commit when its revision is at most that: `consumeDraft` inside the wrapped optimistic step of `sendText`, inside the record commit of `sendMedia`) and the UI's `tx` on the row while it is in the outbox: for `sendText` a host record of kind `sendTx` (`{ chatId, clientKey }`, never sent) committed with the outbox entry, dropped when a committed batch removes an outbox row and the send is no longer in it; for `sendMedia` the `mediaSend` record's `tx`.
- **Attachments**: `attachFile.preview` is kept (at most 16 KB) when the core made none; a video's `width`, `height`, `duration` (and a voice's `duration`) go into `CREATE_UPLOAD`'s metadata, so the server's message has the size the sending row had.

## Not done

- Window per subscription: two subscriptions to one chat share a window and its paging.
- Results across a restart are recovered for `sendText` (by client key), `sendMedia` (its record) and the participant intents (their records' `tx`). `markRead` and `setDialogOpen` re-posted to a later core run again (they are idempotent, so the result is right but it is a second request); the settings intents likewise (their records carry `tx` but are not followed yet).
- A remove retried after its acknowledgement was lost is refused by the server ("not a participant") and settles `rejected` although the person is gone; the refetched roster shows the truth.
- No "leave thread": the server has no chat-leave RPC, and `REMOVE_CHAT_PARTICIPANT` of oneself is allowed only to the thread's creator or a space admin. Chat participants have no role on the wire (`ChatParticipant` is user and date); roles are the space members' (`spaceMembers`).
- `chatMedia` reads disk by scanning and decoding rows (no media column in the replica): a rare filter on a long chat lists only what the newest 2,000 rows hold until `ensure older` or the server page; the whole of a 100,000-message chat would be 387 ms. A `media_kind` column with an index `(chat_id, media_kind, message_id)` would make it one index range read, but is a replica schema change. The list recomputes over the account's resident messages on every message change in that chat.
- Server message search covers one chat (the server has no cross-chat message search); Quick Search's remote section can show people (`searchUsers`) only.
- Draft attachments do not survive a reload. `MessageDraft` stores text and entities only, so it does not fit without a model change in `database/`. Design, no replica schema change: keep the attachment list beside its bytes, in the attachment's own record (`attachments/<id>.json` gains `draftChatId`); `saveDraft.attachmentIds?` sets or clears it, `resume()` keeps attachments that name a draft instead of sweeping them after an hour, `discardAttachment` or a send clears it, and the `draft` query lists them on `DraftRow.attachments?` (`{ attachmentId, attachment }`). Draft text and attachment list are then two durable writes, not one commit; a crash between them leaves either an attachment the draft does not show (swept after an hour) or one it shows without text.
- Edit, delete and react after a restart: a re-posted `tx` runs again (the new core cannot know whether the old one sent it). An edit is harmless; a second delete is refused by the server (`rejected`, `server`); a second reaction add is a server no-op.
- `uncertain` edits and deletes show the confirmed base until sync brings the server's state; reactions are not in sync at all, so an `uncertain` reaction may stay unshown until the message is refetched.
- `countsAsUnread` is not stored in the replica, so the feed cannot honour it; `mentioned` and `silent` are on `MessageRow`.
- Results across a restart for the new durable intents: a re-posted `tx` of a settings intent runs again (harmless: they are replay-safe); a re-posted `sendMedia` with the same client key follows its record.
- Host records exist only because `realtime/transactions/transaction-registry.ts` (owned elsewhere) is a closed allowlist: registering `update_dialog_notification_settings`, `update_dialog_archived` and `read_dialog` there (or letting the host register decoders) would let them use the ordinary outbox; their records would then be `pending` rows.
- Attachment info lives in a JSON file beside the job, not in the replica. The table the media README recommends (`media_upload_jobs` with `transaction_id`) plus an `attachment_info` column would let a send's record, its job and its info commit in one transaction; today the order (bytes, job, info first; then the send's record with its row) makes every crash point recoverable, at the cost of orphan sweeps.
- Membership: the subthread and public-thread fallbacks of the Mac's `ChatParticipantsWithMembersViewModel` (a subthread uses its root's participants; a public thread its space's members) are left to the UI (subscribe to the root or the space). `userGroups` lists groups on the device only (no fetch of a space's groups). Member role changes have no model event yet, so "one member changing" is tested with joins and leaves.
- Media: the web has no synced auto-download settings, so limits and the cache budget come from `media.settings` (Mac defaults). User and space photos are not `media` references yet. Upload progress of a `sendMedia` is on the attachment's resource, not on the row. The browser path (OPFS store, image preparer, Blob handles across a real worker) has not run in a browser.
- Compose: `mediaHints` and compose activity carried through `link`'s multiplexer share one host context, so two multiplexed tabs' nearby sets replace each other.
- Search: the UI merges server hits (`searchServerMessages`) with local ones by message ID; the core does not merge them.
- Acceptance uses `RealtimeClient.execute(transaction, { onAccepted })`.
- Space rows are materialized by `spaces()`; chat and user profile photos are not `media` references.

## Needs fixing elsewhere

- `realtime/client/ping-pong.ts` (`ping`): the ping is registered after `await client.sendPing(nonce)`, so a pong delivered before `send` resolves is unmatched and the connection is dropped 30 s later. The scripted transport's `autoPong` does exactly that, so a long fake-time test reconnects every ~50 s (`model-host.ts` works around it). Register the nonce before sending.
